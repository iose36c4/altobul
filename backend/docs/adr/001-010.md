# ADR 001: PostgreSQL + PostGIS as Primary Database

## Status
Accepted

## Context
Altobul requires geospatial capabilities for:
- User location storage (GEOGRAPHY POINT)
- Geo zone polygons (GEOGRAPHY POLYGON)
- Distance calculations and proximity queries
- ST_Within for zone membership

## Decision
Use PostgreSQL 16 with PostGIS 3.4 extension as the primary database.

## Consequences
- Requires PostGIS-enabled PostgreSQL in all environments
- CI/CD must provision PostGIS container
- All location queries use PostGIS functions (ST_Distance, ST_Within, ST_DWithin)
- Cannot use SQLite for testing (no PostGIS support)

## Alternatives Considered
- MySQL with spatial extensions: Less mature PostGIS compatibility
- MongoDB with geospatial: No ACID for relational data
- External geocoding service: Latency, cost, privacy concerns

# ADR 002: Centralized Authorization Service

## Status
Accepted

## Context
Altobul has complex authorization rules combining:
- Block status (bidirectional, absolute override)
- Relationship levels (NONE → TOKED → MUTUAL_TOKE → MATCH → FRIENDSHIP)
- Resource visibility (PUBLIC, MATCH, FRIENDS, PRIVATE)
- Verification requirements (requires_verified flag)
- Explicit grants for PRIVATE resources

## Decision
Implement a single `AuthorizationService` as the sole authority for all access decisions. All Policies delegate to this service.

## Consequences
- Single source of truth for authorization logic
- Easy to test (96-case matrix)
- No duplicated logic across controllers/policies
- All deny reasons are explicit and traceable
- Performance: O(1) block check + relationship lookup

## Formula
```
ACCESS = NOT BLOCKED(a,b) AND NOT BLOCKED(b,a)
         AND RELATIONSHIP_SATISFIES(visibility)
         AND (NOT requires_verified OR viewer.verified)
         AND (visibility != PRIVATE OR HAS_GRANT(viewer, resource))
```

# ADR 003: Dual Expiration Strategy (expires_at + status cache)

## Status
Accepted

## Context
Resources have TTLs: Toké (48h), Match (7d), Post (24h). Jobs may run late.

## Decision
- `expires_at` timestamp = source of truth (immutable at creation)
- `status` field = denormalized cache updated by scheduled jobs
- All queries use `where('expires_at', '>', now())` NOT `status = ACTIVE`
- Jobs are eventually consistent for status field only

## Consequences
- No resource appears "active" after expiration even if job hasn't run
- Jobs can be retried, delayed, or run in parallel safely
- Status field useful for admin dashboards, analytics
- Migration adds partial indexes on expires_at WHERE status = ACTIVE

# ADR 004: Relationship State Machine (No Match+Friendship Coexistence)

## Status
Accepted

## Context
Spec says: "Match → Friendship" progression. But migrations allowed both ACTIVE simultaneously.

## Decision
Invariant: No pair can have both active Match AND active Friendship.
- Match → Friendship conversion is atomic (transaction + lock)
- Friendship created with `via_match = true`
- Match status set to ENDED (ended_by = initiator)
- Direct FriendshipRequest (without Match) creates Friendship with `via_match = false`

## Consequences
- Chat authorization: MATCH OR FRIENDSHIP both enable chat
- No ambiguous state where both exist
- Conversation continues seamlessly on conversion

# ADR 005: Block Cascade - Access Denial + State Transitions + Grant Revocation

## Status
Accepted

## Context
Blocking must be absolute: "Block overrides everything" per spec.

## Decision
Block creation (single transaction) performs:
1. Creates Block record
2. Cancels active Tokes (sender→receiver and receiver→sender)
3. Ends active Match (status = ENDED_BY_BLOCK)
4. Ends active Friendship (status = ENDED)
5. Ends Conversation (status = ENDED, ended_by_block = true)
6. Revokes all explicit grants (bidirectional)
7. Emits BlockCreated event for async notifications

## Consequences
- Block is irreversible for existing relationships (unblock doesn't restore)
- Historical records preserved (Tokés CONSUMED/EXPIRED, Match ENDED_BY_BLOCK)
- Grants deleted (hard delete) - no audit trail in grant tables
- Block lookup indexed bidirectionally for O(1) check

# ADR 006: Dynamic Profile Fields - Typed Columns + JSONB Denormalization

## Status
Accepted

## Context
Admin-defined fields with types: TEXT, TEXTAREA, NUMBER, DATE, BOOLEAN, SELECT, MULTISELECT, RADIO.

## Decision
- Store typed values in dedicated columns: `value_text`, `value_number`, `value_boolean`, `value_date`
- Add `value_json` JSONB column denormalized for complex queries (written by ProfileFieldService)
- JSONB used for MULTISELECT option arrays, SELECT/RADIO option IDs
- Partial indexes on typed columns for filterable fields
- Field definition validation_rules stored as JSON

## Consequences
- Fast typed queries for NUMBER/DATE/BOOLEAN filters
- JSONB GIN index for complex searches
- Single row per profile-field (no EAV performance issues)
- Adding new types requires migration + service update

# ADR 007: Discovery Pipeline - Geo → Blocks → Visibility → Filters → Order

## Status
Accepted

## Context
Discovery must combine: geography, blocks, profile visibility, verification, preferences, dynamic field filters.

## Decision
Fixed pipeline order (short-circuit where possible):
1. Base: active users, email verified
2. GEOGRAPHY: ST_Within(profile.location, active zone polygons) - PostGIS
3. BLOCKS: NOT EXISTS blocks (bidirectional)
4. DISCOVERABLE: profile.discoverable = true
5. PROFILE VISIBILITY: profile_visibility + relationship check (simplified in SQL)
6. VERIFICATION: profile_requires_verified → user.verified
7. PREFERENCES: Dynamic field filters via DiscoveryQueryBuilder
8. ORDER BY: distance, last_seen, created_at
9. PAGINATE: cursor for distance/recent, offset for others
10. AUTHORIZATION: Final canDiscover() check per result (defense in depth)

## Consequences
- Geo filter first reduces dataset dramatically
- Block check before visibility saves joins
- AuthorizationService final check catches edge cases

# ADR 008: Chat Read-Only After Match Expiry / Friendship End

## Status
Accepted

## Context
Spec: "Match expira → chat se desactiva", "Match → Amistad → chat continúa"

## Decision
- Conversation status: ACTIVE or ENDED (no BLOCKED state)
- ENDED conversations: messages remain readable (read-only)
- New messages rejected if Conversation.status != ACTIVE
- Block → Conversation.end(ended_by_block=true)
- Match expiry → Conversation.end(ended_by_block=false)
- Friendship end → Conversation.end(ended_by_block=false)
- Unread count works normally on ENDED conversations

## Consequences
- Message history preserved for context
- UI shows "Chat ended" banner but allows scrolling
- No new message input on ENDED conversations
- Soft delete on Message (deleted_at) for "unsend"

# ADR 009: Photo Processing Pipeline - Async with Idempotency

## Status
Accepted

## Context
Up to 32 photos/user, max 1024px, WebP conversion, EXIF strip, S3 storage.

## Decision
1. Upload: POST /api/photos → creates Photo(status=PROCESSING) → returns 202
2. Job: ProcessPhotoJob (queue) → validate MIME (finfo) → strip EXIF → resize → WebP 85% → S3 upload
3. Update Photo: storage_key, dimensions, size, status=ACTIVE
4. Idempotency: Idempotency-Key header on upload → prevents duplicate processing
5. Cleanup: Daily job removes status=DELETED photos >24h from S3

## Consequences
- Client polls GET /api/photos/{id} until status=ACTIVE
- S3 keys: `users/{user_id}/{uuid}.webp`
- Signed URLs for private photos (1h expiry)
- Max 32 ACTIVE photos enforced in service (not DB constraint)

# ADR 010: Idempotency Keys for All Mutating Endpoints

## Status
Accepted

## Context
Network retries, double-clicks, mobile reconnections cause duplicate requests.

## Decision
- Required header: `Idempotency-Key: <uuid>` on POST/PUT/PATCH/DELETE
- Middleware checks Redis cache (24h TTL)
- Cache key: `idempotency:{user_id}:{key}`
- Caches: response body, status code, headers
- Returns cached response with `X-Idempotency-Replay: true` header
- Applied to: tokes, matches, friendships, blocks, photos, posts, messages, grants, verification

## Consequences
- Client must generate UUID per user action
- Safe retries without side effects
- 24h TTL covers typical retry windows
- Redis memory: ~1KB per key, negligible
